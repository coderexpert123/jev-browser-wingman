## Resolutions (the S-1/H-2 evaluation the intake asked for)

### S-1(a) — note/payload wording at fallback ends: ONE real finding

The forced table (`forcedNote`, loop.ts; the bench and shipped-default path)
is consistent with same-args resume where resume is intended:
`FORCED_RESUME_LINE` (the default arm, which `error/act-failed` reaches),
`FORCED_BOUNCE_LINE` ("same goal, steps and values plus pick"), and the
deliberate re-plan lines (`FORCED_POST_ACTION_LINE` → "only the steps after
this one"; `FORCED_WRONG_PAGE_LINE`) match what the r19 t9 caller actually
did (log slice: it trimmed, then rewrote, and passed).

The one inconsistency is the **r15 residual**: in optional mode
(`handoff.mode: 'optional'`), a `fallback/step-uncertain` end with
`step_review.why: 'post-action'` falls into the § 3.17 table and reads
`BROWSE_STEP_CALLER_LINE` — "do this step with your browser tools" — which
tells the caller to repeat the action that already ran, the exact thing
`FORCED_POST_ACTION_LINE` forbids. One-branch fix → **WP-1**. It moves no
bench metric (the gauntlet runs forced) and is shipped on correctness grounds.

Payload size was checked as a candidate lever and rejected: r19 t9 forced
caller tokens (out 1545-1576/cell) are comparable to playwright
(1729-1965/cell); the differentiator is the boundary count, not bytes.

### S-1(b) — the resume fast-path: REJECT (a cache for a non-cost)

Measured round costs (r18 Stage D / r19 phases): observe ~7-9 ms, jev
~131-142 ms warm, attach ~17-107 ms per call. A same-args resume's round 1
costs attach + observe + one full chain ask ≈ **0.3 s of loop time**; there is
no separate "entry question" in chain mode — the round ask IS the entry
decision (legacy mode only has a distinct entry ask, and t9-t12 do not run
legacy). The saving from any skip is ≤150-250 ms against a **5-8 s caller
turn** on the same boundary.

The staleness bound is also unanswerable in the honest direction: the settle
machinery (`settleByProbe`, src/core/settle.ts) proves stability only INSIDE a
settle window. Between the two calls sits the caller's multi-second model
turn with nothing watching the page, so "page unchanged since the last round"
cannot be proven at resume time without a fresh observe — which is the thing
being skipped. `ChainMemoryEntry` (loop.ts) stores cursor/acts/clicks/flags,
no page signature; adding one plus a compare would be new state and a new
stale-skip failure mode to save ≤0.25 s. Rejected. The r19 t9 cells never
even exercised a same-args resume — the caller rewrote the step lists per the
notes (trimmed → new `[goal, clauses]` key by design), which is the notes
working as intended.

Refutation note (self-pass, solo round): the strongest counter is "skip the
ask and replay the last decision". Rejected because no decision is ever left
pending at a call end — every end happens after the round's act (or instead
of it), so there is nothing stored to replay; storing the last decision would
add memory state for the same ≤0.25 s.

### S-1(c) — the error/act-failed end: REJECT retry-in-place; accept the boundary

Recorded instances: r18 Stage D D2 (one per cell that round: D2 `act-failed`,
D4 `page-error`; B1 error=1). Zero in r19's t9. The direct observation
(correction C3) is `op: back`, `net::ERR_CACHE_MISS` — deterministic for
POST-response history entries. The safe alternatives do not exist:

- Adapter retry of `goBack`: replays a deterministic failure.
- Reaching the target page by URL: the loop does not know URLs (values may
  not name them; the r15 reload-refusal exists precisely because re-sending a
  POST re-submits the form).
- Downgrading the whole-call abort to a clause bounce (`chainNonCommit`):
  saves zero boundaries (the caller still re-calls) and only relabels the
  telemetry — not worth a behavior change.
- More in-call waiting instead of the post-action/not-ready ends: the r19 t9
  tail already ran `act → wait → wait → post-action bounce` (the cap is
  already spent), and the page only became usable ~7 s later (the caller-turn
  gap), so a third wait (~1-1.5 s) does not reach the recovery time. Also the
  post-action end is r15 machinery the intake's bounds protect.

Verdict: the boundary is **accepted**; the caller's recovery via the notes is
the designed path and it worked on every r19 t9-t12 cell (34/34 forced ok).
Full prize documented for honesty: cutting all 2 non-done boundaries on t9
would be worth ~10-16 s of the 43-47 s wall — and every one of them is a
designed end (post-action, wrong-page, not-ready, login, low-confidence)
whose loosening is out of bounds this round ("no threshold moves", "r15
mechanics stay intact").

### H-1 — resetPages navigate retry: SHIP (WP-2)

Verified shape: `resetPages` (bench/run.ts, ~479-499) sends
`Page.navigate` once through `ctx.observer` with the CdpConnection default
10 s timeout; a rejection (`cdp timeout: Page.navigate`) aborts the
invocation. Bitten twice across rounds (r17-B, r19 attempt 1 — the r19 abort
cost a 2.27 USD partial invocation and forced the 3-file merge). The fix
mirrors the coexistence sentinel's shape (one retry with a longer budget,
`src/cli/coexistence-probe.ts` `SENTINEL_RETRY_MS`): up to 2 retries with
short backoff, retry predicate = the exact timeout message, everything else
rethrows. Scripted-connection test with a fake conn (no Chrome) — the r19
P3-merged stray (0 bytes, untracked) is deleted in passing.

### H-2 — doctor degraded-before: DOCUMENT-AND-SKIP (WP-3)

`fingerprintsReconcile` (src/cli/coexistence-probe.ts, D-4 amended) accepts
`before degraded → reprobe before → matches(freshBefore, after)`. The
documented hole: a persistent **attach-time** write coinciding with a starved
before read is accepted. The intake's candidate tightening ("require the
fresh before to match the original before on the non-null fields") was
evaluated and is **vacuous for that hole**: attach runs BEFORE every
before-side read, so the write is already inside the original before's
successfully-read fields too — original-before[non-null] equals
freshBefore[same] whether or not a write happened. The tightening's real
teeth would be on a write landing between the original before-read and the
re-read (a detach-time write under a starved before) — a class no known
driver in the threat model exercises, at the price of a third read. Per the
intake's bound ("if the only safe fix is a fourth fingerprint round or
heuristics, document and skip"), r20 documents the boundary in the code
comment where the reconcile rule lives. No behavior change.

```ts
// r20 (H-1): retry the reset navigation ONLY on the CDP command timeout —
// `cdp timeout: Page.navigate` is the exact rejection CdpConnection's
// per-command timer produces. Any other rejection (a JSON-RPC error response
// from a failed navigation, a closed socket) is deterministic or fatal and
// rethrows immediately: a retry must not turn a real failure into three slow
// attempts. A timed-out navigate may still have completed; re-navigating the
// SAME startUrl is idempotent, which is why no other reset step re-runs.
export const RESET_NAV_RETRY_BACKOFF_MS: readonly number[] = [2_000, 5_000];
export async function navigateResetWithRetry(
  conn: Pick<CdpConnection, 'send'>,
  sessionId: string,
  url: string,
  sleep: (ms: number) => Promise<void> = (ms) => new Promise((r) => setTimeout(r, ms)),
): Promise<void> {
  for (let attempt = 0; ; attempt++) {
    try {
      await conn.send('Page.navigate', { url }, sessionId);
      return;
    } catch (e) {
      const msg = e instanceof Error ? e.message : String(e);
      if (attempt >= RESET_NAV_RETRY_BACKOFF_MS.length || msg !== 'cdp timeout: Page.navigate') throw e;
      await sleep(RESET_NAV_RETRY_BACKOFF_MS[attempt]);
    }
  }
}
```

    3 sends max (1 + 2 retries), worst added latency ≈ 10 + 2 + 10 + 5 + 10 =
    37 s, still bounded; typical recovery = 1 retry ≈ 12 s (the observed
    flake recovered on an immediate manual re-run).
