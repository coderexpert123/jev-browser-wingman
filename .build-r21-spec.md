## Corrections to the intake (numbered, code-verified)

1. **P-1's mechanism reading is wrong, and the intake's primary fix direction
   ("wait for the page's navigation state to settle before click-family
   acts") addresses the wrong layer.** Verified in the installed
   playwright-core 1.63 source
   (`node_modules/playwright-core/lib/coreBundle.js` ~line 20290): the log
   line "waiting for scheduled navigations to finish" is emitted AFTER
   `action(progress3, point)` — the pointer dispatch has already completed —
   inside `waitForSignalsCreatedBy(..., waitAfter=true, ...)`. It is the
   POST-click wait for navigations created by the click, bounded by the same
   locator timeout. The r20 t9 evidence agrees:
   `bench-results/2026-10-03-r20/evidence/R20-log-slice.jsonl` holds 3
   `act_error` records, all `{"op":"click","head":"locator.click: Timeout
   3000ms exceeded."}` — exactly ONE carries the tail `- waiting for
   scheduled navigations to finish` (the post-click variant); the other two
   carry `- waiting for locator(…)` (the locator never resolved: the document
   swapped between the loop's verify eval, which passed, and Playwright's
   locator — the mid-navigation race). Consequences: (a) the post-click
   variant is fixed by removing Playwright's redundant wait — the loop's own
   `driver.settle` (SETTLE_MAX_MS budget) already owns post-click settling,
   and the CDP adapter never had this wait (`mouseClick` is a raw
   `Input.dispatchMouseEvent` pair); (b) the pre-click variant needs the
   readiness probe; (c) removing the wait makes the NEXT observe start
   mid-navigation more often, and `observeTimed` (loop.ts:1690) has NO retry —
   an observe eval whose context is destroyed mid-navigation throws straight
   to the error end, which would recreate the exact caller-re-call cost the
   item exists to remove. Hence the third edit.
2. **P-2's premise is false: the t6 waits do NOT come from Jev's `ready` noul
   below threshold.** The r20 t6 forced record (slice line
   `2026-10-03T12:30:29.587Z`, browse_step, 9 rounds, 8 wait acts, 8 jev
   calls, 7.7 s) shows readyP 0.42-0.68 across the wait rounds — all above
   `THRESHOLDS.ready` (0.3, `src/contract/constants.ts:51`). The waits are
   Jev's own DECIDED `wait` verb (the action question answers `wait` every
   round; t6's goal text is literally "Start the loading and wait until the
   hidden text appears"), each executed as a blind `sleep(WAIT_OP_MS)` in the
   adapters' `case 'wait'`. The fix therefore targets the wait ACT's
   implementation, not the ready gate — and it needs no "specific pending
   change" detection: the generic r17c growth signal (body text length +
   element count) discriminates t6 exactly (#finish's "Hello World!" landing
   changes both; the animated loading bar changes neither).
3. **P-4's "run it against the r16-r20 recorded logs" is only partly
   possible.** `WingmanLogRecord` (`src/contract/types.ts:172-240`) carries
   per-round probabilities and element ids only — never the ask request
   (state + question criteria) nor the raw answer document. A replay through
   `createDefaultAsk`/`parseJevAnswers` from those logs is impossible. What
   the old slices support is a threshold-MARGIN distribution report (how many
   recorded rounds sat within ±0.1 of each threshold — the treadmill
   quantification). Full decision replay requires freshly captured
   (request, answer) pairs; `createWingman`'s `opts.ask` is injectable
   (`src/lib.ts:33,64`), so capture mode wraps `createDefaultAsk` with a
   recorder. Scope: margins mode over the existing slices
   (`refs/backup/r16-results` … `r20-results` `evidence/*log-slice*.jsonl` —
   verified present for r16 (log-invB2-forced), r19 (P1-P3 slices), r20

4. **The bbc/npr captcha matchers are not recorded anywhere machine-readable.**

## Resolutions (the item-by-item evaluation the intake asked for)

### P-1 — SHIP as three edits (D1-D3). "Settle before click" alone is rejected

The settled-before-click variant (run `settleByProbe` before every click) is
rejected on cost: settle's stability rule costs ~300 ms minimum per act even
on an already-complete page. The chosen shape costs one eval (~10 ms) on the
fast path. `Page.waitForNavigation` racing is rejected outright: the proven
failure is a wait AFTER the click, not a missing wait for a future
navigation.

### P-2 — SHIP as the wait-act growth poll (D4). Loop-level changes rejected

The loop already owns round economics; the adapters own act semantics. A
loop-level "one settle-poll instead of N wait rounds" would need new
round machinery, new telemetry, and decision-path changes for zero extra
discrimination over polling inside the existing wait act. Budget chosen as
3000 ms (= SETTLE_MAX_MS, "the existing settle budget" per the intake): t6's
~5 s load folds ~5-8 wait rounds into ~2; a dead page's wait act costs 3 s
instead of 1 s, bounded by the existing round caps (the ready-gate arm is
additionally bounded by READY_MAX_WAITS = 2). An "exit early when the page
reads settled" refinement was considered and REJECTED: it would kill the t6
win (the loading page reads readyState complete + stable sig while the
content loads via XHR — the poll must outlive that stillness).

### P-3 — SHIP as the scoped detection (D5). "Primary interactive content" gate rejected

Requiring the challenge to be the page's primary interactive content would
false-negative the common inline case (a real reCAPTCHA checkbox at the
bottom of an otherwise normal checkout form — dozens of legitimate
candidates). The chosen gates are precise-biased; recall rests on the
per-round `blocked` noul question (asked every round, `src/core/questions.ts:34`),
which is the same layering today's `otpText`/password signals use. The
false-negative risk analysis is D6 and the live-site validation is the
operator-visible cloud stage.

### P-4 — SHIP the harness (D7-D9); no grader change this round

The OG-9 bimodality evidence (0.66 → 0.48 re-grades of the same step) plus
the r13 storm history is exactly the case the intake's replay gate exists
for; no threshold move ships without its report. The harness is the
deliverable.

### P-5 — SHIP behind the KB flag with the D12 accept/reject bar

Config-key gating was considered and rejected (a dead experimental config
surface if the heuristic is rejected; the KB flag plus a binary
merge-or-revert decision is cleaner and matches every prior round's
convention). `verify`'s implicitRole mirror is UNGATED, following the r19
`ondblclick` precedent exactly (a gated verify against an ungated-enumerated
record would throw stale on every heuristic element).

## Design decisions (exact literals)

**D1 (P-1a, playwright adapter only).** The three element-targeted Playwright
click call sites — `click` (playwright.ts:515), the `check`/`uncheck` label
click (playwright.ts:534), `dblclick` (playwright.ts:584) — change from
`rec.page.locator(el.path).click(timeout)` to pass
`{ timeout: ACT_TIMEOUT_MS, ...(KB_PW_NOWAIT ? {} : { noWaitAfter: true }) }`
where `timeout` is the existing module-level `{ timeout: ACT_TIMEOUT_MS }`
constant (rename it `timeout` stays; compose the spread). `fill`, `select`,
`press`, `hover`, `upload`, `scroll_to` are untouched (no evidence; `press`'s
`noWaitAfter` is documented no-effect; `hover` already disables waitAfter
internally). The CDP adapter gets NO equivalent — it has no post-click wait
to remove.

**D2 (P-1b, both adapters).** New exported probe in
`src/core/page-scripts.ts`: reuse `buildSettleProbeExpression()` as-is (it
already returns `{readyState, sig}`). New constant
`PRE_CLICK_SETTLE_MS = 4_000` in `src/contract/constants.ts`. Guard shape,
inserted in the ELEMENT-targeted path after the element lookup and BEFORE
the verify evaluation, only when
`op === 'click' || op === 'dblclick' || op === 'check' || op === 'uncheck'`:

```ts
if (!KB_PW_PRECLICK) {
  const probe = await evaluateOnPage(rec, buildSettleProbeExpression()) as { readyState?: string } | null;
  if (!probe || (probe.readyState !== 'interactive' && probe.readyState !== 'complete')) {
    await settleByProbe(async () => { try { return await evaluateOnPage(rec, buildSettleProbeExpression()) as {readyState: string; sig: string}; } catch { return null; } }, PRE_CLICK_SETTLE_MS);
  }
}
```

(playwright.ts form above; the cdp.ts mirror uses `this.evalIsolated` +
`this.probeScrollGrowth`'s try/catch shape and `settleByProbe` — cdp.ts
already imports both settle helpers for its scroll/settle cases.) Proceed
regardless when the budget expires — a stuck page then fails exactly as
today (the "stuck page must still bounce" bound holds). The guard adds one
eval (~10 ms) on a loaded page and is a no-op structurally otherwise.

**D3 (P-1c, loop).** `observeTimed` (loop.ts:1690) gains a bounded,
settle-backed retry, gated by `KB_OBS_RETRY` and by a fast-fail test:

```ts
const observeTimed = async (pageId: string): Promise<Observation> => {
  const t = now();
  try {
    const obs = await driver!.observe(pageId);
    return finishTiming(obs);
  } catch (e) {
    if (KB_OBS_RETRY || (now() - t) >= 2_000) throw e;   // slow failure = wedge, not nav
    for (let i = 0; i < 2; i++) {
      await driver!.settle(pageId, OBS_RETRY_SETTLE_MS);
      try { return finishTiming(await driver!.observe(pageId)); } catch { /* retry */ }
    }
    throw e;
  }
};
```

(written with the existing telemetry lines preserved — the `finishTiming`
body is today's three telemetry statements; the builder keeps them running
exactly once per returned obs). New constant `OBS_RETRY_SETTLE_MS = 500` in
`src/contract/constants.ts`. Worst added wall: 2 × (500 + fast CDP error) ≈
1.2 s; a wedged renderer's 5 s eval timeout is never retried (the ≥2 s
gate). Applies to both call sites (2701, 3371) automatically.

**D4 (P-2, both adapters).** New constant `WAIT_GROWTH_MS = 3_000` in
`src/contract/constants.ts`. The `case 'wait'` body changes in BOTH adapters:

```ts
case 'wait': {
  const baseline = KB_PW_WAIT_GROWTH ? null : await probeScrollGrowth(rec);
  if (baseline === null) {
    await sleep(WAIT_OP_MS);
  } else {
    await waitForScrollGrowth(() => probeScrollGrowth(rec), baseline, WAIT_GROWTH_MS);
  }
  break;   // cdp.ts: return;
}
```

(exact r17c precedent: `KB_PW_GROWTH_WAIT ? null : await probeScrollGrowth(rec)`
at playwright.ts:401; cdp.ts:459-462 mirrors with its own
`this.probeScrollGrowth`). No new telemetry: the poll cost lands in `actMs`
and is read from there in analysis (a wait act's actMs may now read up to
~3000 — the WP-7 metrics read must not treat that as a defect). The loop is
untouched; `waits` counting, WAIT_MAX_PER_CALL, and the ready gate are
untouched.

**D5 (P-3, enumerate only).** Inside `computeSignals`
(page-scripts.ts:402-439), body-local additions (all inside the stringified
`enumerate` body per the purity contract):

```js
var KB_CAPTCHA_SCOPED = false;
var CHALLENGE_MIN_AREA = 16000;
```

The two arms keep CAPTCHA_RE unchanged but compose the scoped gates
(`var scoped = !KB_CAPTCHA_SCOPED;`):

- iframe arm: `CAPTCHA_RE.test(src) && (!scoped || (src.indexOf('size=invisible') === -1 && isVisible(iframes[fi]) && area(iframes[fi]) >= CHALLENGE_MIN_AREA))` where `area(el)` reads one `getBoundingClientRect` (w×h, rounded not required).
- id/class arm: unchanged RE test on `(id || '') + ' ' + (className || '')`, then when scoped: skip tags script/style/template/noscript/link/meta, require `isVisible(node)` and `area(node) >= CHALLENGE_MIN_AREA` (rect read only after the RE hits — the RE-first order keeps the cost on matching candidates only).

Gate semantics: `isVisible` is the body's existing function; a 0×0 or
`display:none` container fails it; the reCAPTCHA v2 checkbox (304×78 =
23712), hCaptcha (303×78 ≈ 23634) and Turnstile (300×65 = 19500) all pass
16000; the v3 badge (256×60 = 15360) fails BOTH the area gate and the
`size=invisible` exclusion. Consumers unchanged: loop.ts:3421's
`obs.signals.captcha` hard block and the `blocked` noul question behave
identically on a true signal. `src/contract/types.ts:80` comment updates to:
"challenge-indicative iframe src or element id/class, visible and ≥16000 px²
(`size=invisible` excluded)".

**D6 (P-3 false-negative risk analysis — explicit, ships in the WP report
and the cloud stage).** The hard signal becomes deliberately
precision-biased; accepted FN windows: (1) a real challenge whose iframe is
not yet sized/visible at enumerate time (mid-load) — the signal fires on a
LATER round's observe; (2) vendor geometry drift (the 16000 px² gate and
`size=invisible` are vendor-controlled) — the recon runs at every validation
round and re-derives the matched set; (3) challenges rendered entirely
inside cross-origin frames are detected via the frame ELEMENT only (iframe
traversal is out of scope this round — unchanged from today). The recall
net is the per-round `blocked` question, which every round request carries;
a page the scoped signal misses can still be classified blocked by Jev from
state/text, exactly as OTP/password signals work today. The r20-confirmed
hard-block pins (chain.test.ts:661 drives `captcha: true` through the loop)
are untouched and must stay green.

**D7 (P-4 harness).** New tracked `bench/grader-replay.mjs` (ESM, imports
from `../dist/` at run time, probe6b-replay import pattern). Three
subcommands:

- `capture --out <file> [--url <page-url>]... [--task <fixture-page> <step-text>]...`:
  launches `launchEphemeralChrome` (headless), builds
  `createDefaultAsk({ apiKey })` from the env key, wraps it in a recorder
  that appends one JSON line per ask: `{ts, tool, request, response, ms}`.
  Drives `createWingman({ env, ask })` with `runStep`/`runDo` calls over the
  fixture server pages (and any `--url` live pages). Output files are
  UNTRACKED (`.calib/` by convention) — they contain page text.
- `replay --capture <file> --thresholds <overrides.json> --report <file>`:
  per captured round, parses the recorded response's answer map and
  evaluates the threshold comparisons (target bar, done/step_done/ready/
  error/right_page nouls) under the override set against the recorded
  baseline set; reports per-round would-change rows plus a summary.
  The report header states the mirror's scope honestly: threshold
  comparisons on recorded probability sets, NOT the full evidence-rule
  cascade.
- `margins --slices <glob> --report <file>`: reads log slices (r16-r20
  `evidence/*.jsonl`), extracts the recorded probability fields, and
  histograms each threshold's margins (count of rounds within ±0.05/±0.1 of
  `ready` 0.3, `stepDoneWithEvidence` 0.5, `done` 0.85, `target` 0.5).

**D8 (P-4 drift self-check — the check that can fail).** Every capture line
also records the loop's actual round decision (from the returned result /
log record: action choice + commit vs non-commit + end reason). `replay`
with NO `--thresholds` (baseline set) must reproduce every recorded
decision class from the recorded probability sets; ANY mismatch exits 1 with
the offending round printed. This is the mirror-drift guard: if the loop's
rule order moves and the mirror goes stale, the self-check fails before any
candidate threshold is trusted. The self-check is exercised by a unit test
that corrupts one captured probability and asserts exit 1.

**D9 (P-4 replay-gated change protocol — for FUTURE rounds, recorded
here).** A threshold/rule change may ship only with: a fresh capture on the
pages that evidence the miscalibration, a replay report showing the candidate
set flips the targeted bounces to commits WITHOUT flipping any recorded
advance/commit on completed calls, and the self-check green. Nothing in r21
meets this bar yet; the WP runs capture + margins and REPORTS.

(element count over `max_elements`) makes TWO `askWithCost` calls, but the

after the first multi-ask round shifted by one, silently (unmatched rounds

`recover`/`round`), the merge is the exported pure `mergeCapture`, and it
consumes the round's CONTINUATION asks (`target`, `option`) into the same
round, merging answer maps (request 2 never repeats the verb question —
amendment 2026-09-21h). A round whose `jevMs` never moved ended BEFORE its

proven: the two new pins in `tests/grader-replay.test.ts` read red against

the no-ask round stealing the next round's ask) and green after. Note: D7's
capture line description now carries `stage`, and old capture files (no
`stage`) still replay — `mergeCapture` re-derives the stage from the
request's question keys when absent.

**F2 (observe-retry documented bound was wrong).** D3's "~1.2 s worst
added wall" assumed the < 2 s fast-fail check applies to every retry; it
guards only the FIRST failure (loop.ts `observeTimed`). The inner retries'
observes carry no speed check, so two slow inner failures stack to roughly
first fast failure + 2 × (500 ms settle + ~5 s observe) ≈ **11 s** —
navigation-shaped, bounded. The BEHAVIOR is accepted (bounded, deterministic
reasons unchanged); only the documentation is corrected, in
`src/contract/constants.ts` (the `OBS_RETRY_SETTLE_MS` comment) and the
`observeTimed` doc comment in `src/core/loop.ts`. This block supersedes any
earlier "~1.2 s" wording in D3-related notes.

**F3 (SVG className blindness in the captcha id/class arm).** D5's
"id/class arm: unchanged RE test on `(id || '') + ' ' + (className || '')`"
is superseded: on an SVG element `className` is an `SVGAnimatedString`
object (stringifies to `'[object SVGAnimatedString]'`), so a captcha class
carried by an SVG never matched. The arm now reads
`el.getAttribute('class') || ''` (works for HTML and SVG); the scoped
gates (tag skip-list, `isVisible`, `CHALLENGE_MIN_AREA`) are unchanged and
